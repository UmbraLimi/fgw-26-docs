## Progress
Turned the style/website-design discussion into a settled visual system, working top-down from
structure to detail. Every fork was decided from a **rendered in-browser mockup** (a localhost static
server viewed via the `/chrome` bridge) rather than from labels — which the operator explicitly valued
and which decided choices (editorial vs engineered, the four serifs, palette, scale, buttons) in one
pass each. Structure: multi-page primary, SPA-smooth via Astro View Transitions; the `/spa` long-scroll
was first reserved, then abandoned. IA: `/`, `/work` (+ `/work/<slug>`), `/method`, `/about`,
`/contact` — lead-gen only (commerce + Stripe dropped), blog designed-for but deferred. Substrate: no
shadcn, Tailwind v4 CSS-first `@theme`. Visual: "quiet authority / editorial" — Fraunces + Inter,
warm-neutral + ember palette (light+dark), a modular scale, and a full component layer (ink-primary
buttons with ember reserved for the top CTA; boxed inputs; hairline no-shadow cards; prose; nav/footer).
The style guide is defined as the **definitive single source**; its canonical form will be a rendered
`/styleguide` page built at scaffold, where contrast gets WCAG-verified. Agreed sequence: decide
components now (A) → scaffold (B) → review/refine the guide live. Operator also granted standing
authority for autonomous `/r-commit`. Closed with scaffold sequenced as the next action; no product code
written this conv.

## Learnings
- **Rendered mockups beat labels for design forks.** The operator couldn't judge "editorial vs
  engineered" from words; a side-by-side in-browser render settled it, and every later fork went the
  same way. Pattern: for a visual decision, serve a localhost mockup and screenshot via the bridge.
- **"Design done" ≠ "task closed", and a premature ✅ is a trust cost.** Marking `[STYLE-THEME]`
  complete after only tokens — before buttons/components and any guide artifact — was caught by the
  operator. A row stays open until its implementation/review are real.
